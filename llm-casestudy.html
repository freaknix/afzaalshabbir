Executive summary

This case study documents an iterative evaluation of a locally deployed cybersecurity-focused language model. The work progressed from a fixed set of Cyber Security knowledge questions to SOC alert investigations, comparison with human analyst decisions, and a broader Qwen3.5-9B evaluation involving multiple operational alert types.

The central objective is not to demonstrate that an LLM can replace a SOC analyst. It is to establish where the model can assist L1 workflows, what failure modes emerge when evidence is incomplete or ambiguous, and how dataset quality and evaluation controls can be improved systematically.

1. Research objective and evaluation principles

The research question evolved from a basic capability question—“Can the model answer cybersecurity questions?”—to a more operational and safety-relevant question: “Can the model assist with security investigations while keeping its conclusions traceable to the available evidence and communicating uncertainty appropriately?” Two human’s were presented with the answers and based on their analysis, following were the key take aways.

1.1 Core research questions

  • Knowledge reliability: Does the model provide technically correct Cyber Security explanations and distinguish established facts from assumptions?

  • Investigation usefulness: Can it summarize SIEM evidence, identify plausible causes, suggest relevant correlations and request missing information?

  • Evidence fidelity: Does it preserve exact IP addresses, hostnames, accounts, event IDs, timestamps, versions and log details without inventing or transferring them?

  • Uncertainty handling: Does it distinguish confirmed events, suspected malicious activity, benign explanations and unresolved root causes?

  • Decision safety: Are classifications and recommendations proportionate to the available evidence and operational impact?

  • Repeatability: Does the same model and prompt configuration produce materially consistent outputs when the same case is rerun?

1.2 Essential evaluation distinction

DO NOT COLLAPSE THESE QUESTIONS
A security event can be real without being malicious. A detection can correctly identify a condition while the condition is benign, authorized or operational. A root cause can remain unknown even when the event itself is confirmed.



The traditional TP/FP/FN/TN terminology is meaningful only after defining the detection target and the ground-truth label. For an alert-only sample, the evaluator generally cannot measure false negatives or true negatives because those require examples where the detector did not raise an alert. The evaluation therefore separates: (1) event/detection validity; (2) security significance or maliciousness; (3) root-cause confidence; and (4) recommended disposition.

Data-quality principle

Improving model performance is not only a matter of changing model parameters. The quality of the input evidence, labels, case boundaries, context and evaluation criteria determines whether an apparent improvement is genuine. The dataset must be improved before model-to-model comparisons can be trusted.

  • Preserve original raw logs and alert metadata; do not replace them with summaries alone.

  • Use stable case IDs and keep each input, model output and analyst disposition linked to the same ID.

  • Separate observed facts, analyst hypotheses, threat-intelligence enrichment and final adjudicated conclusions.

  • Record time zones, source timestamps, ingestion timestamps and collection delays.

  • Label each CVE/package/host individually when a single alert aggregates multiple findings.

  • Anonymise usernames, hostnames, IPs and client identifiers before sharing or publishing.

  • Keep incomplete or disputed cases as unresolved; do not force them into TP/FP labels.













3. Scenario A — 30-question cybersecurity knowledge and repeatability test

A fixed set of 30 cybersecurity questions was supplied to the model. Answers were recorded over a two-week period in three different intervals. The researcher reports that the model produced the same results consistently when the questions were repeated.

3.1 What this experiment demonstrates

  • Repeatability under the tested conditions: the observed answers did not materially vary across the two-week observation period.

  • Prompt stability: the model appears to interpret the fixed questions and response expectations consistently.

  • A useful baseline for knowledge-oriented evaluation before moving into more complex SOC tasks.

3.2 What it does not yet demonstrate



  • Calibration: repeated confidence statements do not establish that the confidence values correspond to actual probabilities of correctness.

  • Robustness: a fixed question set does not test paraphrases, contradictory evidence, prompt injection, long context or multi-case contamination.

  • Generalization: 30 questions are a useful pilot, but do not represent the full range of cybersecurity knowledge or SOC operations.

SAFE CONCLUSION FOR SCENARIO A
The two-week exercise provides preliminary evidence that the model is repeatable for the tested 30 cybersecurity questions under the configuration used. This is promising for consistent knowledge assistance, but correctness and breadth must be established through independent answer-key scoring and a larger, more varied test set.



Recommended next refinement: classify each question by domain and difficulty; establish an answer key with authoritative references; score each answer against required concepts; repeat each question multiple times; and record prompt, model, quantitation and decoding settings. Add paraphrased versions and deliberate “insufficient evidence” questions.



4. Scenario B — Human analyst versus LLM SOC investigation comparison

An initial spreadsheet compared human analyst decisions with LLM analysis across 12 investigation entries in three week time period on two different models. The examples included firewall authentication, Windows auditing, application-control events, vulnerability applicability, Kerberos failures, network availability and security configuration findings. Certain details were omitted from initial investigations to check how LLM behaves.

Observation

Detection validity vs maliciousness

The model sometimes labelled benign machine/service logons as TP because the events had genuinely occurred.

The classification target must be defined before scoring.

Uncertainty collapsed into a label

The model should preserve “pending validation” rather than force a binary verdict.

Some cases identified plausible stale credentials, system maintenance or VPN connectivity explanations and requested corroborating logs.

4.2 Why no accuracy percentage is reported

The initial comparison contains missing human labels, missing or incomplete LLM decisions, and at least one case-to-response mismatch. It also uses TP/FP labels without a consistently documented definition. The comparison is therefore useful for qualitative error discovery, but it is not sufficiently complete or adjudicated to support a reliable accuracy, precision, recall or F1 score.

RESEARCH LESSON
Human analyst decisions are an important reference, but they should not automatically be treated as ground truth. Where analysts disagree, the case should be adjudicated using the original telemetry, environmental context and documented decision criteria.

5. Scenario B, C & D — Qwen3.5-9B Q4_K_M SOC investigation outputs

The latest supplied output file (new-model-results-18-nov-26(3).txt) contains 12, 53 & 32 numbered case sections respectively. The sequence omits case numbers 17 and 21, and the recorded answers for cases 7–10 and 32 are blank in the supplied extract. The supplied model identification is Qwen3.5-9B with Q4_K_M quantisation; the output file itself does not record all runtime, prompt and decoding settings.

5.1 Capabilities observed

  • Log and alert summarisation: the model extracted key fields such as event IDs, accounts, source addresses, failure codes, hostnames and affected services.

  • Investigation hypothesis generation: it proposed plausible benign and malicious explanations, including stale credentials, automated password guessing, configuration errors and network connectivity issues.

  • Correlation planning: it suggested examining related Windows event IDs, host ownership, successful logons, EDR findings, firewall policies and packet captures.

  • Operational recommendations: it generated immediate checks, longer-term controls and requests for missing information, often in structured JSON.

  • Basic uncertainty recognition: several responses explicitly noted that the supplied logs did not prove compromise, malicious intent or root cause.

6. Key research findings across scenarios

Finding

Why it matters

Proposed intervention

Event/attack conflation

A valid event may be benign; “TP” depends on what the detector was intended to detect.

Use separate labels for event validity, maliciousness, root cause and disposition.

Overconfident conclusions

The model sometimes assigns high confidence despite missing host ownership, authorization, file hash or successful-login evidence.

Require evidence-linked confidence and permit “unknown / pending validation”.

Context contamination

Facts may be carried from one investigation into another.

Run single-case and multi-case tests; enforce case IDs and isolated contexts.

Unsupported inference

A proxy signature, ZIP transfer or authentication failures do not alone prove compromise.

Require each conclusion to cite the exact supporting event or data point.

Premature remediation

Destructive actions such as reimaging or broad blocking may be disproportionate before validation.

Separate investigation, containment, eradication and recovery; require human approval for high-impact actions.

Incomplete output records

Blank answers, skipped case numbering and incomplete labels undermine reproducibility.

Add automated completeness and schema validation before scoring.



7. Data quality improvement — from raw alerts to benchmark-ready cases

The next phase should turn the collected 50 use cases into an adjudicated evaluation dataset. The dataset should be built in layers so that the model is tested on evidence quality and decision quality separately.

Layer

Required fields / controls

Quality check

A. Raw evidence

Original alert, expanded log, source event, timestamps, asset identifiers, relevant configuration and telemetry.

No detail added by the summariser; timestamp/time-zone provenance retained.

B. Context

Asset criticality, host role, approved activity, change window, known services, network exposure and policy context.

Context is sourced and timestamped, not inferred.

C. Evidence extraction

Observed facts, missing fields, contradictions, duplicate/aggregated events and external enrichment.

Every fact linked to a source record; enrichment clearly marked.

D. Independent labels

Event validity; maliciousness; cause; disposition; confidence; supporting evidence.

Two reviewers where feasible; disagreements adjudicated.

E. Model input/output

Stable case ID, exact prompt, model build, quantisation, system prompt, runtime, sampling settings and full raw answer.

No missing output, cross-case mapping or silent truncation.

F. Evaluation record

Claim-level support, classification, uncertainty, action safety, structured-output validity and reviewer notes.

Scoring rubric applied consistently and blind to model identity where practical.





8. Quantitative evaluation plan

Once the 50 cases have been curated and adjudicated, the model should be evaluated on a held-out test set. Avoid tuning prompts on the final test set. Use separate development, validation and test partitions, grouped by incident or source environment where possible to reduce leakage.

8.1 Core metrics

Metric

Operational definition

Notes

Classification performance

Precision, recall, F1, specificity and confusion matrix for clearly defined labels.

Do not calculate FN/TN from alert-only examples; include known missed detections and benign non-alert examples.

Evidence fidelity

Supported factual claims ÷ all checkable factual claims.

Score claims individually; preserve source references.

Unsupported-claim rate

Unsupported factual claims ÷ all checkable factual claims.

Separate harmless omissions from fabricated high-impact facts.

Context contamination rate

Responses containing facts from another case ÷ responses tested.

Use controlled mixed-context experiments.

Uncertainty preservation

Correctly retained unknown/pending states ÷ cases requiring uncertainty.

Assess whether the model abstains or asks for relevant evidence.

Confidence calibration

Brier score and/or expected calibration error on adjudicated binary/multiclass outcomes.

Only if confidence is collected consistently and treated as a probability.

Recommendation safety

Expert-rated appropriateness, proportionality and reversibility of proposed actions.

Flag destructive or broad actions lacking evidence and approval.

Repeatability

Agreement of material claims and decisions across repeated runs.

Consistency is not correctness; report both separately.

JSON/schema validity

Valid structured outputs ÷ outputs requested in the schema.

Check required keys, types, enums and parse errors.

Latency and resource use

Time to first token, total response time, tokens and hardware use.

Useful for deployment feasibility, not reasoning quality.



8.2 Controlled experiments

  1. Baseline: one investigation per isolated conversation, using a fixed prompt and frozen model/runtime configuration.

  2. Evidence-constrained prompt: require the model to list observed facts, inferences, unknowns and evidence references before providing a disposition.

  3. Mixed-context challenge: place multiple case records in one context and measure whether case facts leak between outputs.

  4. Incomplete-evidence challenge: remove one or more key fields and measure abstention quality, confidence reduction and clarification requests.

  5. Human-assistance study: compare analyst decisions with and without model support, recording time, error detection, decision changes and reviewer confidence.

  6. Model comparison: compare Qwen3.5-9B Q4_K_M with other model builds only when the same data, prompt, runtime settings and scoring rubric are used.

11. Research positioning and limitations

PROPOSED RESEARCH POSITIONING
Applied AI safety and evaluation for cybersecurity operations: measuring evidence fidelity, context integrity, uncertainty preservation, adaptive tool use and human oversight in high-impact security workflows.



The combined work provides an applied practitioner perspective across LLM investigation, classical/ML behavioral detection, autonomous security agents and enterprise AI governance. It is relevant to empirical evaluation, safeguards and human-AI oversight research. It does not, on its own, establish experience in frontier-model training, mechanistic interpret-ability or theoretical alignment research.

Limitations to state openly

  • The 30-question exercise establishes reported consistency, not independently verified correctness.

  • The initial 12 & 53 cases which were provided to LLM, had initial finding mentioned in the description, which were corrected in the following investigations.

  • The Qwen3.5 output text has 32 numbered case sections, but LLM changed behavior and stopped producing results in json format for some investigations, which is another limitation of model.

  • Confidence percentages generated by the model are self-reported and are not calibrated probabilities unless verified empirically.



12. Conclusion

Scenario A — 30-question, two-week repeatability exercise

The model was provided with 30 cybersecurity questions and its answers were recorded over a two-week period. The researcher observed that it produced the same results consistently. We can safely conclude that, under the tested setup, the model demonstrated promising response repeatability for this fixed set of cybersecurity questions. We cannot conclude from consistency alone that every answer was correct, comprehensive or appropriately calibrated. A verified answer key and claim-level scoring are required to establish factual accuracy.

Scenario B,C & D — SOC investigation assistance

The human-versus-LLM comparisons and the Qwen3.5-9B Q4_K_M investigation outputs demonstrate promising capabilities for L1-level SOC investigation assistance. The model can summaries alerts, extract salient technical details, propose plausible root-cause hypotheses, suggest relevant log correlations, recommend investigation steps and request missing information. These are useful support functions for a first-line analyst, particularly for structuring an initial investigation.

At the same time, notable challenges remain. The observed outputs include confusion between a valid event and malicious activity, overconfident classifications despite missing evidence, premature or overly broad remediation recommendations, and occasional case-detail contamination or response-to-case mismatch in the broader evaluation artifacts. These issues must be addressed before the model is relied on for autonomous disposition or operational response.

Overall conclusion

SAFE OVERALL CONCLUSION
The results are promising for SOC L1 analyst’s training. The current evidence does not justify autonomous incident classification, closure or high-impact remediation. The next phase is to improve the 50-case dataset with scaled to thousands of cases dataset and through evidence preservation, independent adjudication, consistent labels and case isolation, then evaluate the model using claim-level evidence fidelity, classification metrics, calibration, abstention and action-safety measures.
